# AGENTS.md

Orientation for an AI agent picking this repository up cold. Read this first,
then follow the links. **It deliberately does not restate the deep docs** - it
points at them, so there is one copy of each fact and nothing to keep in sync.

Last verified: 14 September 2026, against a running dev server and a clean
`tsc -b --noEmit` and `vite build`.

## 1. What this is in three sentences

A directory of people who build technology and the real work they have done:
the problem, the decisions, and the number that changed. The pitch is "like
Dribbble, but what you are looking at is the real work, not a picture of it."
Two deployables live in one repository - a React SPA that runs with no backend
at all, and an Express/MongoDB API that is finished but **not yet wired to the
SPA**.

| | Path | Stack | State |
|---|---|---|---|
| SPA | `/` | React 19, Vite 7, Tailwind v4 | live, no backend needed |
| API | `/server` | Node 20+, Express 5, MongoDB 7, Zod | built and smoke-tested, unused by the SPA |

## 3. The one constraint that shapes everything

**The SPA has no runtime dependency beyond `react` and `react-dom`.**

Check `package.json` before you reach for anything. The router, icons, modal,
focus trap, image downscaler and the combobox are hand-rolled on purpose. This
rule routinely conflicts with generic front-end advice - "use Framer Motion",
"install lucide-react", "add shadcn/ui", "use react-select". **The rule wins.**
If you believe an exception is warranted, say so and ask; do not install first.

The API may use libraries freely. It just may never import from the SPA's
source tree - it reads `server/fixtures/*.json`, regenerated by
`npm run export:fixtures`.

## 4. Getting it running

```bash
npm install
npm run dev          # SPA on http://localhost:9800, no database needed
```

That is enough for nearly all front-end work. The API additionally needs a
MongoDB **replica set** (publish runs in a transaction) - see §10 of
`docs/PROJECT_CONTEXT.md`.

```bash
npm run build            # tsc -b && vite build
npm run lint             # tsc -b --noEmit
npm run export:fixtures  # src/data/*.ts -> server/fixtures/*.json
```

## 5. How a change is verified

**There is no test suite for the SPA.** Do not claim a change works because it
compiles. Drive a real browser and assert:

1. No console errors on every route.
2. `document.scrollWidth === document.clientWidth` at 360 / 390 / 768 / 1024 /
   1440. No horizontal overflow.
3. The full flow still completes: register → panel → publish → the entry
   appears on the home grid and the index.

Each of those three has caught a real bug. For the API: `cd server && npm run
test:smoke` (125 assertions against an ephemeral replica set).

**Two traps when verifying in a browser:**

- Vite HMR leaves **stale errors in the console** after a multi-step edit. An
  error that names a symbol you have already removed is almost always stale -
  reload in a fresh tab before believing it.
- Measuring layout while the browser pane is hidden (`document.hidden === true`)
  or before layout settles gives false overflow readings. Give it ~600ms per
  route and check `document.hidden` first.

## 6. The domain model in one screen

Three axes, plus two facets that belong to the person. The string ids below are
literal and shared across SPA, API and database.

- **Craft** (`role`), 8 values: `design` `engineering` `product` `data` `infra`
  `quality` `growth` `research`. Set **per entry, not per person** - a designer
  who shipped a routing engine files it as developer work.
- **Topic**, 17 values in one array (`Work.topics`) but **two kinds**:
  - `industry` (11): `saas` `ai` `banking` `finance` `erp` `energy` `mobility`
    `healthtech` `gaming` `climate` `security`. Carries a business case.
  - `practice` (6): `leadership` `design-ops` `devex` `accessibility` `hiring`
    `reliability`. Discipline work with no revenue line of its own.

  One storage axis, **two separate filter controls**. Keeping the storage
  unified is what lets the two-per-topic quota stay a single counter.
- **Business model**, 10 values. Exists because craft + topic cannot tell you
  whether two projects are comparable.
- **Experience** - banded, never an exact number (`src/data/experience.ts`).
- **Language** - working language, seeded per country from `Person.location`.

**Filter semantics:** every facet is an array. Empty means no opinion. Within
one facet values are **OR**-ed; across facets everything is **AND**-ed.
`skills` is the deliberate exception and stays AND-ed within itself, because a
skill list is a spec rather than a shortlist.

## 7. Product rules that are the product

These are not arbitrary constraints. Relaxing one changes what the product is,
so raise it before you do. `docs/BUSINESS.md` has the reasoning.

1. **Two published entries per topic, per person.** Enforced client-side for UX
   and server-side by a guarded atomic update. The seeded fixtures respect it
   too - do not add seed data that breaks it.
2. **Every entry states problem, decisions, outcome.** "It never shipped" is a
   valid outcome; the seed data deliberately includes cancelled projects,
   accepted regressions, and a migration stopped at 60%.
3. **Proof points are "Results claimed", never verified facts.** We cannot
   verify a number, and presenting claimed figures as verified would be the
   most damaging thing this product could do.
4. **Generated covers by default,** so confidential work is not second-class
   and the grid does not become a design competition.
5. **Simulated data says it is simulated.** The traffic panel is generated and
   says so on screen.

## 8. House style

Beyond `CLAUDE.md`, these are enforced conventions rather than preferences:

- **No em dashes in anything a reader sees.** Headlines, labels, buttons, body
  copy, seed prose, alt text. `grep -r "—" src` must return nothing. Use a
  spaced hyphen or restructure the sentence.
- **No hard-coded colours.** Tokens live in `src/index.css` under `@theme`.
  Use `color-mix(in oklab, var(--color-pop-lime) 55%, transparent)` rather than
  an `rgba()` literal.
- **Eyebrows are rationed** to roughly one small uppercase label per three
  sections. Every section carrying one is what makes a page read as templated.
- **Labels are visible, never `sr-only`,** on form and filter controls.
- **Dropdowns are `Combobox`, never a native `<select>`.**

## 9. Non-obvious things that will bite you

The full list is §11 of `docs/ENGINEERING.md` - 14 invariants, each one a bug
that already happened. The five most likely to catch a new agent:

1. **In-page `<a href="#...">` anchors break routing.** The router reads
   `location.hash`, so a jump link inside a page route navigates away from that
   route. Scroll imperatively with `scrollIntoView`.
2. **A popover positioned `absolute` is clipped by any scrolling ancestor** -
   which is exactly what the join modal is. `Combobox` measures from the
   trigger and positions `fixed`.
3. **A capture-phase `scroll` listener fires for descendants too.** Closing a
   popover on scroll will close it when the user scrolls the popover's own
   list, unless you exclude events originating inside it.
4. **A pagination signature must cover every filter.** Miss one and the list
   keeps its old offset when that filter changes.
5. **`Person.categories` holds industries only.** `withDerivedTopics()` unions
   in the topics of a person's published work; without it every practice topic
   reports zero people while showing case studies.

## 10. Where the seams are

If you are adding something, these are the places designed to be extended:

| To do this | Touch this |
|---|---|
| Add a field to one craft's form | a `FieldSpec` in `src/data/portfolioSchemas.ts`. No component, validator or migration change. |
| Add a craft | `ROLES` in `taxonomy.ts`, a schema under the same id, `SKILL_SUGGESTIONS`, and a motif case in `WorkCover.tsx`. TypeScript points at all four. |
| Add a topic | `CATEGORIES` in `taxonomy.ts` with its `kind`. |
| Wire the SPA to the API | `src/hooks/useAccount.tsx`. Its context contract already matches the API's shape - replace the `localStorage` bodies with fetch calls and **no component needs to change.** |
| Change similarity scoring | `src/lib/similar.ts` **and** `server/src/modules/work/queries.ts`. Two implementations, required to stay identical. |
| Change what a card shows | `src/lib/workMapper.ts` (`workFromDraft`) is where a schema field becomes card data. |

## 11. Current state, and what is not done

**Working and verified:** home page, portfolio index, case study pages, profile
pages grouped by topic, the authoring panel, join flow, and standing About /
Changelog / Privacy pages. 40 seeded people, 54 seeded case studies, 40 of
those people carrying work.

**The main remaining piece of work is wiring the SPA to the API.** The SPA
still reads `localStorage`. See §12 of `docs/PROJECT_CONTEXT.md` for the
ordered gap list, which also covers what the API needs before production
(email verification, password reset, Redis-backed rate limits, a tuned CSP).

**Routing is path-based** (`/work/slug`), not hash-based. The host must serve
`index.html` for unknown paths; `public/_redirects` and `vercel.json` do that,
and `npm run build` also writes `dist/sitemap.xml`.

**Four crafts are open** - Designer, Developer, Product, DevOps. The other four
show as "Soon" and are filtered out by `isRoleLive`, though their seeded
entries stay in the fixtures.

**A moderation console lives at `#/admin`** with a review queue (rule flags plus
reader reports), entry and people lists, site settings (contact, editable copy,
which crafts are offered) and an audit log. It has **no access control in the
SPA** and says so on screen; the real gate is `requireModerator` in the API.
The matching API module is `server/src/modules/moderation/`, covered by the
smoke test, and `docs/DATABASE.md` documents the three new collections.

**Recent changes worth knowing about,** newest first. The user-facing version of
this list is the in-app Changelog page (`src/pages/ChangelogPage.tsx`):

- Path routing, per-route metadata, a real 404, robots.txt and a generated
  sitemap. Self-hosted fonts, so the only third-party request left is the
  seeded portrait host.
- Moderation notices and appeals: a decision now tells the author why, and an
  overturned appeal reverses it.
- Cookieless funnel counters (`src/lib/analytics.ts`) and a Funnel view in the
  console, so first-entry completion is measurable.
- Terms, content policy and an accessibility statement.
- Email verification and a report rate limit on the API. Publishing needs a
  verified address; drafting does not.
- A moderation console, reader reports, and the API module behind them.
- Every filter facet became multi-select, with OR-within / AND-across
  semantics. `Filters` is all arrays now.
- `practice` left the topic dropdown and became its own control, without
  splitting the storage axis.
- Portfolio cards are clickable as a whole, via a stretched link inside the
  existing action button so the accessible name stays on one control. Skill
  chips opt back out with `relative z-10`.
- Native `<select>` was replaced everywhere by a hand-rolled `Combobox` with an
  in-popover filter above 6 options.
- Experience and language filters added; `Author` carries `years` and
  `languages` so a person facet can narrow work through its author.
- Profile pages added at `#/people/:id`.
- An anti-slop pass: 155 em dashes removed, eyebrows rationed, case-study
  chapters promoted from micro-labels to real headings.

## 12. Working agreements

- **Do not relax a product rule to make an implementation easier.** Raise it.
- **Do not add a runtime dependency to the SPA.** Ask first.
- **Do not claim something works because it compiles.** See §5.
- **Update the docs you invalidate.** If a change makes a line in
  `PROJECT_CONTEXT.md` or `ENGINEERING.md` false, fix that line in the same
  change. A stale handover is worse than none.
- **Say what you did not do.** Partial work described accurately is useful;
  partial work described as complete is a trap for the next agent.
