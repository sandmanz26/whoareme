## 1. Konteks Infra (dikonfirmasi client)

**Infrastruktur deployment:**

- **Local development:** MongoDB **standalone** (bukan Docker, install native). Shared instance dengan backend lain.
- **Production:** VPS sendiri, MongoDB standalone (shared dengan backend lain di VPS yang sama), nginx sebagai reverse proxy.
- **Deploy flow:** `git pull → npm run build → pm2 restart` (manual, tanpa CI/CD).
- **CDN/Cloudflare:** belum dipakai, mungkin ditambahkan nanti.
- **Docker config:** file `docker-compose.yml` dipertahankan sebagai alternative reference, tidak dihapus.

**Konsekuensi arsitektural untuk fix plan:**

1. **MongoDB standalone = transactions tidak tersedia.** `session.withTransaction()` butuh replica set. Fix untuk operasi multi-write harus pakai **compensating pattern** + atomic `findOneAndUpdate` (optimistic locking), bukan transaction.
2. **Single VPS, single instance** = rate limiter in-memory OK, Redis tidak perlu.
3. **nginx 1-hop** = `TRUST_PROXY=1`, `req.ip` reliable, S1 (IP spoof) low risk sekarang — perlu revisit saat Cloudflare ditambah.
4. **No CI/CD** = setiap batch fix wajib di-verify manual dengan `npm run lint` + (untuk backend changes) `npm run test:smoke`.

## 4. Critical Findings

### 🔴 C1. Traffic dashboard setiap user selalu kosong — **FIX**

- **File:** `server/src/usecase/user/Traffic/index.ts:25,45`
- **Root cause:** `TrafficDaily.aggregate([{ $match: { ownerId: userId, ... } }])` — `userId` adalah string dari `req.user!.id`, tapi `TrafficDaily.ownerId` adalah `Schema.Types.ObjectId`. Di `.aggregate()`, Mongoose **tidak auto-cast** (berbeda dengan `.find()`).
- **Dampak:** Fitur traffic panel di PanelPage **mati total**. Setiap user melihat 0 profile views, 0 work opens, perWork array kosong.
- **Fix:** Cast ke `new Types.ObjectId(userId)` di kedua `$match` stage.
- **Verifikasi:** Buat 1 traffic event dari visitor lain, buka traffic panel, harus muncul angka > 0.

### 🔴 C2. JWT verifikasi mengabaikan payload — **DEFER (improvement nanti)**

- **File:** `server/src/middleware/userAuth.ts:33,37,76,82` + `config/index.ts:12` + `usecase/user/Auth/index.ts:179-180`
- **Konteks:** Keputusan desain client: 1 user = 1 device (login kedua kick device lama). Nanti akan di-improve ke multi-device.
- **Action sekarang:** Tidak ada perubahan.
- **Follow-up list (nanti):**
  - Compare `payload.sub === user._id.toString()` di middleware.
  - Simpan `jti` hash di DB, bukan raw signed string.
  - Dukung multi-session (array session per user).
  - Turunkan TTL dari 30d ke 15 menit + implementasi refresh rotation.

### 🔴 C3. Zero transactions — **FIX dengan compensating pattern (bukan transaction)**

- **Scope:** `WorkUsecase.Publish/Unpublish/Delete`, `ModerationWorkUsecase.SetPublished`, `ModerationPeopleUsecase.SetSuspended`, `DecideAppeal`, `UpdateProfile` fan-out.
- **Konteks:** MongoDB standalone → transactions tidak tersedia. Harus pakai pattern alternatif.
- **Pattern yang akan dipakai:**
  1. **Atomic check-and-set** dengan `findOneAndUpdate({ ..., guard_condition })` untuk langkah pertama. Return null = gagal langsung.
  2. **Compensating rollback** di catch block untuk langkah berikutnya yang throw.
  3. **Logging critical error** jika rollback juga gagal (untuk pickup oleh reconcile script).
- **Reconcile script** (`npm run db:reconcile`) menjadi safety net wajib — dijalankan cron mingguan di VPS.
- **Verifikasi:** Smoke test (`npm run test:smoke`) harus lulus untuk flow publish, unpublish, moderation.

### 🔴 C4. Moderator republish bypass quota 2-per-topic — **FIX**

- **File:** `server/src/usecase/moderation/Work/index.ts:54-74`
- **Root cause:** `SetPublished(true, ...)` increment `counts.topicUsage.<topic>` **tanpa `$nor` guard** seperti `WorkUsecase.Publish`.
- **Dampak:** Moderator bisa republish entry yang membuat `topicUsage` > 2 (melanggar non-negotiable rule `CLAUDE.md §7`).
- **Fix:** Tambah `$nor: topics.map(t => ({ ["counts.topicUsage." + t]: { $gte: 2 } }))` ke filter guard. Jika gagal match, throw `409 topic_quota_exceeded`.
- **Verifikasi:** Smoke test skenario: user publish 2 di topik X → mod unpublish 1 → user publish 1 baru di X → mod republish yang pertama → harus 409.

### 🔴 C5. `express.static("uploads")` di root tanpa prefix — **FIX**

- **File:** `server/src/server.ts:29`
- **Root cause:** Mounted di `/` (bukan `/uploads/*`). MIME extension diambil dari `path.extname(file.originalname)` (attacker-controlled). Tidak ada `Content-Disposition: attachment`.
- **Risiko:** Path traversal + potential stored XSS pada origin API jika file SVG/HTML lolos MIME filter.
- **Fix:**
  ```ts
  app.use("/uploads", express.static("uploads", {
    dotfiles: "deny",
    index: false,
    setHeaders: (res) => res.setHeader("Content-Disposition", "inline"),
  }))
  ```
  Di `multer/index.ts`: hardcode extension dari MIME, bukan dari originalName.
- **Breaking change:** URL thumbnail berubah dari `/thumbnails/xxx.jpg` → `/uploads/thumbnails/xxx.jpg`. Perlu update `${API_BASE_URL}/thumbnails/${filename}` references di code.

### 🔴 C6. CORS mengizinkan no-Origin dengan credentials — **AS-IS**

- **File:** `server/src/server.ts:19-26`
- **Keputusan client:** Biarkan — tool server-to-server (curl, Postman) tetap diloloskan untuk QA testing.
- **Mitigasi aktif:** Rate limiter + auth via Bearer token (bukan cookie). CSRF classical tidak possible.
- **Catatan:** OK selama rate limit + token-based auth tetap kuat.

### 🔴 C7. `react-hot-toast` tidak di-install — **FIX**

- **Lokasi:** approved stack di `docs/FRONTEND_RULES.md`, tapi `grep -r "react-hot-toast" src/` → zero hits.
- **Dampak:** Semua mutation silent (moderator unpublish 500 → tidak ada feedback, dll).
- **Fix:**
  1. `npm install react-hot-toast`
  2. Mount `<Toaster/>` di `src/components/layout/Shell.tsx`
  3. Tambah `onSuccess` / `onError` toast di setiap `useMutation`:
     - `useMyWork` (saveDraft, publish, unpublish, delete)
     - `useMyProfile` (patchMe)
     - `useAdmin` (semua mod decision + resolve report + decide appeal + settings)
     - `useAccount` auth mutations
     - Verification email mutations
- **Verifikasi:** Trigger error 500 artificially (misal: short-term matikan server) → UI harus munculkan error toast.

### 🔴 C8. Axios client tanpa interceptor — **FIX**

- **File:** `src/lib/api/client.ts:1-20`
- **Yang hilang:** timeout 10s, response interceptor normalisasi error, 401 → clear auth + redirect, 429/500 handling.
- **Fix:** Implement sesuai pattern di `docs/FRONTEND_RULES.md:131-160`:
  ```ts
  export const api = axios.create({
    baseURL: import.meta.env.VITE_API_URL,
    timeout: 10_000,
    headers: { "Content-Type": "application/json" },
  })

  api.interceptors.request.use((config) => {
    const token = useAuthStore.getState().token
    if (token) config.headers.Authorization = `Bearer ${token}`
    return config
  })

  api.interceptors.response.use(
    (response) => response,
    (error) => {
      if (error.response?.status === 401) {
        useAuthStore.getState().clearAuth()
        window.location.replace("/signin")
      }
      const message = error.response?.data?.message ?? error.message ?? "Something went wrong"
      return Promise.reject(new Error(message))
    },
  )
  ```
- **Catatan:** Project pakai React Context (`useAccount`), bukan Zustand. Adaptasi: gunakan event emitter atau direct localStorage clear + navigate.
- **Verifikasi:** Expire token di DB manual, trigger mutation → UI harus redirect ke `/signin`.

### 🔴 C9. Password-reset token pakai `JWT_SECRET` sebagai HMAC key — **FIX**

- **File:** `server/src/utils/hash.ts:10-12` + `config/index.ts:11`
- **Root cause:** `hashToken` = `HMAC-SHA256(JWT_SECRET, token)`. Satu key dipakai untuk 2 purpose kriptografi berbeda.
- **Dampak:** Jika JWT_SECRET bocor → attacker bisa mint JWT bebas DAN hitung hash reset token DB untuk brute force.
- **Fix:**
  1. Tambah env `TOKEN_HASH_SECRET` (minimum 32 char).
  2. Update `hashToken()` pakai `TOKEN_HASH_SECRET`.
  3. Minimum length `JWT_SECRET` naikkan dari 16 ke 32.
  4. Migration: existing reset tokens akan jadi invalid (acceptable — user minta ulang).
- **Verifikasi:** Request password reset, confirm token berhasil.

### 🔴 C10. Login tahan credential stuffing — **FIX**

- **File:** `server/src/middleware/rateLimit.ts:14-21`, `routes/v1/user/index.ts:27`
- **Root cause:** `authLimiter` = 20/IP/15min dengan `skipSuccessfulRequests: true`. Credential stuffing dengan password yang bocor → mayoritas attempt sukses → limiter tidak hitung → unlimited.
- **Fix:**
  1. Second limiter khusus `/login` dengan key `req.body.email` (max 5 failed / 15 min / email).
  2. Matikan `skipSuccessfulRequests` untuk `/login`.
  3. Account lockout: setelah 10 consecutive failed per email, lock selama 15 menit (field `lockedUntil` di user doc).
- **Verifikasi:** Script loop 11 failed login untuk 1 email → request ke-12 harus di-reject meski password benar.
